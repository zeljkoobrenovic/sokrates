# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sokrates is a source-code analysis tool ("code spelunking, inspired by grep, adding structure on top of regex source code searches"). It scans a codebase, builds a JSON analysis configuration, and generates a suite of HTML reports (overview, duplication, file size, logical decomposition, dependencies, contributors/git history, concerns, findings, metrics, controls, trends). It ships as both a CLI and a JavaFX GUI explorer. See [sokrates.dev](https://sokrates.dev).

## Build & test

Java 17, Maven multi-module build.

```bash
mvn clean install                              # build all modules + run tests, produces fat jars
mvn install -DskipTests                        # build without tests (as Dockerfile does)
mvn -pl codeanalyzer -am install               # build one module and its dependencies
mvn -pl codeanalyzer test                      # run tests for a single module
mvn -pl codeanalyzer test -Dtest=JavaAnalyzerTest                     # single test class
mvn -pl codeanalyzer test -Dtest=JavaAnalyzerTest#testExtractUnits    # single test method
```

Build artifacts (fat jars via maven-assembly + jar-with-dependencies):
- `cli/target/cli-1.0-jar-with-dependencies.jar` — CLI (main class `nl.obren.sokrates.cli.CommandLineInterface`)
- `codeexplorer/target/codeexplorer-1.0-jar-with-dependencies.jar` — JavaFX GUI (main class `nl.obren.sokrates.codeexplorer.CodeExplorerLauncher`)

Tests use JUnit Jupiter + Vintage (mixed JUnit 4/5). The parent pom forces `-Duser.country=US -Duser.language=us` via `argLine` — locale-sensitive formatting tests depend on this.

No external runtime dependencies: dependency/visualization graphs are rendered **client-side with Mermaid.js** (loaded from CDN), so report generation no longer shells out to an external process. (Graphviz/`dot` was previously required; it has been removed — see "Dependency graphs" below.)

**The one-shot command family** (added 2026-09/10; the recommended entry points — the older step commands remain):

`-dataOnly` (on `generateReports`, `analyze`, `analyzeGitRepo` and `analyzeLandscape`/`updateLandscape`, where it applies to the per-URL analyses AND to the landscape itself) stores only `reports/data/data.zip`: `generateReports(cmd, conf, reportsFolder)` sets `CodeAnalyzerSettings.dataOnly` (a long-dormant setting that `BasicSourceCodeReportGenerator`/the index export already honoured) and `DataExporter.setDataOnly`, which makes `exportSourceFile` return early (no `html/Structure.html`, no `src/viewer.html`) and `zipDataFolder` skip `data-preview.html`; the CLI then skips `generateVisuals` and `generateAndSaveReports` entirely, so the reports folder holds exactly `data/data.zip` (asserted by `AnalyzeCommandTest.dataOnlyStoresJustTheDataZip`, which also checks a later full run restores everything). For the landscape itself, `updateLandscape(args, …)` passes the flag to `LandscapeAnalysisCommands.update(root, conf, metadata, dataOnly)` → `generateReport(…, dataOnly)`: the `LandscapeReportGenerator(…, dataOnly)` constructor returns right after `exportData` (so `report()` is never used), `LandscapeDataExport.setDataOnly` skips the `files-explorer.html`/`repositories.html` pages it renders next to the data, `exportLandscape` only packages `data/` (`zipLandscapeDataFolder(folder, writePreview=false)`, no `data-preview.html`), no `contributors/` folder is created, and virtual sub-landscapes are generated data-only too (`config.json` + `data/data.zip`, which is all a parent's Sub-landscapes tab reads). Like the repository flag, it does not delete report files left by an earlier full run. A `config.json` already in `-destFolder` is copied into the fresh clone before analysis, so user edits survive re-runs (the cloner's fetch-and-reset path is therefore unused by this command). The output layout (`config.json` next to `reports/`) is exactly what the landscape discovery expects, so N `analyzeGitRepo` runs in one folder + `analyzeLandscape` = a landscape. `analyze(cmd, root, …)` returns the reports folder and `logReportLocation` prints the `file://` link (for analyzeGitRepo, of the kept copy). HTTPS credentials come only from the `SOKRATES_GIT_TOKEN`/`SOKRATES_GIT_USER` env vars (default user `x-access-token`). Covered by `AnalyzeGitRepoCommandTest`, which clones from a local bare repo (offline). Note the history extractor skips the parentless root commit, so a one-commit repo yields an empty `git-history.txt` and no contributors report.
- **`-postAnalysis <command>` / `-ai claude|codex|gemini` / `-aiPrompt <text>`** (on `analyze`, `analyzeGitRepo`, `analyzeLandscape`/`updateLandscape`, `analyzeGitHubOrg`, `analyzeGitLabGroup`): `cli/PostAnalysisHook`. `analyze(cmd, root, skipGitHistory, repoUrl, keptFolder)` ends with `runPostAnalysisHook`, which runs the command via `/bin/sh -c` (`cmd /c` on Windows) in the source root — for the clone-and-analyze step inside the temporary clone, **before** `_sokrates/` is moved to the kept folder, so the agent sees the source and whatever it writes under `_sokrates/` travels with the analysis — with `inheritIO` and the env `SOKRATES_REPO_URL`/`REPO_NAME` (`GitRepoMetadata.reportName()`, or the folder name)/`SRC_ROOT`/`ANALYSIS_FOLDER`/`REPORTS_FOLDER`/`OUTPUT_FOLDER` (the kept folder, or the analysis folder for a local analysis). `postAnalysisCommand(cmd)`: an explicit `-postAnalysis` wins, else `PostAnalysisHook.aiPresetCommand(agent, prompt)` (claude `-p … --permission-mode acceptEdits --allowedTools …`, `codex exec --full-auto …`, `gemini -p … --yolo`; default prompt "run a full scan" = the sokrates-skills full scan; unknown agent → error, no hook). A non-zero exit is logged and never fails the analysis. **Incremental** (`cli/PostAnalysisState`, `_sokrates/post-analysis.json`: command, head, ranOn, exitCode): before running, `runPostAnalysisHook` reads the state kept with the analysis (the kept folder for a clone — the clone's fresh `_sokrates` has none — else the analysis folder) and skips when `covers(command, head)` (same command, same `PostAnalysisState.headCommit(root)` via JGit, last exit 0) unless `-aiForce`; `-aiMaxRepos <n>` caps `postAnalysisRuns` per `run(args)` invocation (reset there), later repositories are analyzed without the hook and get no state, so the next invocation picks them up. After a run the state is saved into the analysis folder (it moves with the analysis); a skipped clone keeps its earlier state file because the move only replaces namesakes. A tree without `.git` has head "" and is never skipped. Agent-agnostic by design: Sokrates only runs a command line; the agent CLI and the skills must be installed on the host (the Docker image has no agent). Covered by `PostAnalysisHookTest` (presets; the command runs in the clone and its output is kept; per-repository in a landscape with one failing command; a local `analyze`; skip-until-head-moves/-aiForce/changed command/failed run; `-aiMaxRepos` across two invocations).

- `analyzeLandscape` / `updateLandscape` — aggregate multiple analyses into a landscape report. - `updateLandscapePeopleConfigByUserName` — build/update `config-people.json` by grouping contributor emails that share a display name (userName) under one entry (additive: appends new emails only). Grouping is by a normalized display-name key — case- and **whitespace-insensitive** (`PeopleConfigByUserNameUpdater.userNameKey` strips ALL whitespace + lowercases), so `"James Lesslar"`, `"JAMES LESSLAR"` and the no-space commit form `"JamesLesslar"` collapse to one entry. Every grouped email — **plus the entry's own `email` field** — is added to `emailPatterns` (as a `\Q…\E` literal), so a person collapses by email and never depends solely on a userName match. This key **must stay in sync with `PeopleConfig.userNameKey`** (the analyzer's runtime plain-`userName` matching in `getPerson` uses the same strip), or the config would group two identities the analyzer then treats as distinct.
- `updatePeopleConfigByUserName` — single-repository version of the above; reads only the repo's `git-history.txt` (run after `extractGitHistory`, no `generateReports` needed) and writes `_sokrates/config-people.json`
- `extractGitHistory` / `extractGitSubHistory` — produce `git-history.txt` consumed by history analyses, plus the optional sidecar `git-commits.txt` (one line per commit: `<sha> <first line of the commit message>`, constant `GitHistoryUtils.GIT_COMMITS_FILE_NAME`, parsed by `GitHistoryUtils.getCommitMessagesFromFile`). The sidecar — rather than extra `git-history.txt` columns — keeps older parsers of the main file working; consumers must treat it as optional (older extractions don't have it). `extractGitSubHistory` copies it verbatim into each split folder (sha-keyed, so the superset map stays valid). A second optional sidecar, `git-commit-trailers.txt` (`GitHistoryUtils.GIT_COMMIT_TRAILERS_FILE_NAME`, read by `getCommitTrailersFromFile` into `sha → List<CommitTrailer>`), holds the commit message **trailers** verbatim — one line per (commit, trailer): `<sha> <Key>: <value>` (e.g. `Co-Authored-By: Claude <noreply@anthropic.com>`, `Signed-off-by: …`) — plus two pseudo-trailers: `Committer: Name <email>` written only when the committer differs from the author (squash/rebase merges, bot merges), and `Message-Signature: <line>` for tool signature lines in the body that aren't trailers (e.g. `🤖 Generated with [Claude Code](…)` — older Claude Code wrote only this, no `Co-authored-by`), found by `GitHistoryUtils.extractMessageSignatures` (generic line-start heuristic `^\W*(generated|made|created|built) (with|by|using) …`, subject line excluded; the analysis config decides which tool it names, and such values resolve to AI agents only — an unmatched signature is dropped, never a person). Trailers are parsed from the full message by the pure `GitHistoryUtils.extractTrailers` (last paragraph, `Key: value` lines, indented continuation lines folded; a partly-prose final paragraph still yields its trailer lines, so a few false positives like `cases: …` are expected and consumers filter by key — `CommitTrailer.hasKey` is case-insensitive since agents write `Co-Authored-By` and `Co-authored-by` alike). Raw and config-free on purpose: re-extraction is the expensive step, so which keys count as co-authors / which values are AI agents is decided at analysis time via `fileHistoryAnalysis.coAuthors` (`CoAuthorsConfig`: `enabled` (default true; false makes `getCoAuthorsBySha` return an empty map, which hides every co-author feature downstream), `trailerKeys` + named `aiAgents` regex patterns, defaults in code — documented in docs/configuration.md). `GitHistoryUtils.getCoAuthorsBySha(historyFile, config)` resolves the sidecar into `sha → List<CoAuthor>` (`{name, email, agent}`; `agent` = configured agent name, `bot` when only the `bots` list matches, `null` for a person). Person co-authors go through the **same** identity pipeline as commit authors — `normalizeEmail` (ignore → anonymize/transform) + `applyPeopleConfig` (config-people.json remap), both factored out of `parseLine` — so a person's authored and co-authored commits collapse to one identity. `getAuthorCommits` attaches them to `AuthorCommit.coAuthors` (sidecar read once per history file via a path-keyed static cache, next to the JVM-wide `updates` cache) and `GitContributorsUtil.getContributorsPerTimeSlot` counts commits with `hasAiCoAuthor()` into `ContributionTimeSlot.aiCoAuthoredCommitsCount` (per year/month/week/day, per scope, serialized in `analysisResults.json`; `LandscapeAnalysisResults.updateContributors` sums it across repos). Co-authors do NOT count as slot contributors. Same rules as `git-commits.txt`: written only for commits that produced file lines, optional for consumers, copied verbatim by `extractGitSubHistory`.
- `createConventionsFile` / `exportStandardConventions` — work with analysis conventions

Typical flows: single repo `analyze` → edit `config.json` → `analyze` (or the individual `extractGitHistory` → `init` → `generateReports`); from a URL `analyzeGitRepo -url …` (re-run = fresh clone + kept config); many repos `analyzeLandscape -urls repos.txt` (re-run refreshes everything; add a line to add a repo); whole organizations `analyzeGitHubOrg -org a -org b` / `analyzeGitLabGroup -group x/y` (one landscape per org + a parent). Note `GitHistoryUtils.getHistoryFromFile`'s static cache is keyed by the history file's absolute path (like the co-authors cache), so two analyses in one JVM (explorer GUI, tests) don't share history.

## Module architecture

The Maven module dependency chain is `common → codeanalyzer → reports → cli → codeexplorer`. All code lives under the `nl.obren.sokrates` package.

- **common** — foundation: JSON (Jackson via Jersey), rendering utilities, chart/3D-force/x3d rendering helpers, IO. No Sokrates-specific domain logic.
- **codeanalyzer** — the analysis engine. Defines the configuration model, scopes the codebase, runs language-specific and cross-cutting analyses, produces a `CodeAnalysisResults` object.
- **reports** — consumes `CodeAnalysisResults` and renders HTML reports + exports data (JSON). Also builds landscape reports aggregating many analyses.
- **cli** — command-line entry point and git history extraction.
- **codeexplorer** — JavaFX GUI front-end; depends on cli, codeanalyzer, common.

## How analysis works (the big picture)

1. **Configuration** — `CodeConfiguration` (`codeanalyzer/.../sourcecode/core/`) is the central serialized model, read from/written to `config.json` (`CodeConfigurationUtils.DEFAULT_CONFIGURATION_FILE_NAME`). It declares: file `extensions`, `ignore` filters, scope aspects (`main`, `test`, `generated`, `buildAndDeployment`, `other`), `logicalDecompositions`, `concernGroups`, `goalsAndControls`, and `tagRules`. Most analysis behavior is driven by this JSON, not by code changes. The user-facing reference for both `_sokrates/config.json` and `_sokrates_landscape/config.json` (every key, defaults, examples, and the companion `config-tags`/`config-teams`/`config-people.json` files) is **[docs/configuration.md](docs/configuration.md)** — update it when changing these config models. **User-visible behaviour changes** (anything that can change what an existing configuration selects or where output goes) get a dated entry in **[CHANGELOG.md](CHANGELOG.md)** (newest first; what changed, why, what stays the same, what to check).

2. **Scoping** — `scoping/ScopeCreator` plus `Convention`/`ConventionUtils` apply standard + custom conventions to classify files into aspects. A convention is written into a new `config.json` only when a file matches it at init — except `ScopingConventions.SOKRATES_OUTPUT_CONVENTIONS` (`_sokrates/`, `_sokrates_landscape/`, the git export txt files, `sokrates_*.json`), which `ensureSokratesOutputIgnored` adds unconditionally at init (also with custom conventions) and, as an in-memory safety net for older configurations, when `generateReports` loads a config; before, the first run's reports landed in the second run's main scope because `_sokrates/` did not exist when the tree was scanned (`ScopingConventionsSokratesOutputTest`, `AnalyzeCommandTest.theAnalysisOutputIsNeverAnalyzed`). An *aspect* (`sourcecode/aspects/`) is a named set of source files defined by path/content filters; aspects are the unit that decompositions and concerns are built from. **A filter's `pathPattern` is matched against `SourceFileFilter.matchingPath(sourceFile)`: `"/" + relativePath`** (the path below the source root with a leading separator, so `.*/[Tt]ests/.*`-style patterns work on top-level folders too), never the whole path as loaded — before, an absolute source root (Docker's `/code`, any absolute `-srcRoot`) put the folders above the repository into the matched path and a checkout under a `tests`/`docs` folder had every file classified by them (`SourceFileFilterMatchingPathTest`). A `SourceFile` that was never relativized falls back to its full path. The sokrates-skills config scripts (`preview_config.py` etc.) mirror this rule and must stay in sync.

3. **Language analyzers** — `LanguageAnalyzerFactory` maps file extensions to a `LanguageAnalyzer` subclass (`sourcecode/lang/<language>/`). 40+ languages are supported. Each analyzer implements:
   - `cleanForLinesOfCodeCalculations` / `cleanForDuplicationCalculations` — strip comments/blank lines
   - `extractUnits` — find functions/methods (for unit-size and conditional-complexity metrics)
   - `extractDependencies` — heuristic, regex-based dependency extraction
   - `getFeaturesDescription` — declares which analyses the language supports
   To add language support: create a `LanguageAnalyzer` subclass and register its extensions in `LanguageAnalyzerFactory`. Unknown extensions fall back to `DefaultLanguageAnalyzer`.

4. **Analysis orchestration** — `analysis/CodeAnalyzer.analyze(...)` runs a sequence of `Analyzer` subclasses in `analysis/files/` (`BasicsAnalyzer`, `DuplicationAnalyzer`, `FileSizeAnalyzer`, `UnitsAnalyzer`, `LogicalDecompositionAnalyzer`, `ConcernsAnalyzer`, `ControlsAnalyzer`, `ContributorsAnalyzer`, `FileHistoryAnalyzer`), each populating part of `CodeAnalysisResults` (`analysis/results/`). `CodeAnalyzerSettings` toggles expensive analyses (duplication, correlations, complex analyses).

5. **Reporting** — generators in `reports/.../generators/statichtml/` each take `CodeAnalysisResults` and emit an HTML report; `dataexporters/` emit JSON. `landscape/` aggregates multiple project results into a portfolio-level report.

## Landscapes & sub-landscapes

A **landscape** aggregates many repository reports into a portfolio view. `updateLandscape` (CLI) runs `LandscapeAnalysisCommands.generateReport(analysisRoot, configFile)`: `LandscapeAnalyzer.analyze(configFile)` reads each repository's data — `analysisResults.json`, `config.json`, and `text/aspect_*.txt`/`text/mainFilesWithHistory.txt` — into a `LandscapeAnalysisResults` (`List<RepositoryAnalysisResults>`); then `LandscapeReportGenerator(results, tagGroups, folder, reportsFolder).report()` writes `index.html` + tabs + `contributors/` + `visuals/` + `data/` into the `_sokrates_landscape/` folder. A repository's identity is its `metadata.name`.

The Overview tab includes a **repositories circle-packing chart** (`addRepositoriesBubbleChart` in `LandscapeReportGenerator`), placed right after the extensions section ("Contributors per File Extensions (past 30 days)") and before any custom iframes: each repository is a bubble **sized by main lines of code** and **colored by main language** (`LanguageColors.getColor`, a deterministic per-language hue — no curated map), plus a color **legend** listing every language present (`repositoryLanguagesByLoc`). It's iframed from a self-contained `visuals/repositories_bubble_chart.html` rendered via `VisualizationTemplate.renderZoomableCirclesColored` (data embedded inline, leaf colors honored). The circles are **grouped by main language** (`buildLanguageCircles` → the pure, unit-tested static `groupByLanguage(List<RepositoryBubble>)`): one zoomable group circle per language (ordered by total main LOC desc) containing that language's repositories as leaves. **Only the leaves are colored** by the language hue; the group circle stays uncolored (depth gradient) — the template's `inheritedColor` checks a node before its ancestors, so a leaf's explicit color wins while the group falls back to the gradient. Group label = `[<lang>] (N repositories)`; each leaf's label = the repo name and it carries a `tooltip` (`<name> · <LOC> LOC · <lang>`) — an optional `VisualizationItem` field (`@JsonInclude(NON_EMPTY)`, so it doesn't bloat charts that don't use it, e.g. the all-files circles). Repos with no detectable main language or zero main LOC are skipped. `zoomable_circles_colored.html` **clips each label to its bubble** (`labelForRadius`, re-applied per zoom level) so text never overflows, and shows the full `tooltip` (falling back to `name`) on hover via a `<title>` — leaf circles use `pointer-events: all` so the hover tooltip fires on them. These behaviors are shared with the `zoomable_circles_all_files.html` view. (The separate sub-landscape circle builders — `buildVirtualLandscapeCircles`/`buildFolderPathCircles` — are unrelated and still group the Sub-landscapes tab's circles by virtual landscape / folder path.)

### Landscape search/filter syntax (repositories & contributors reports)

Both client-rendered landscape lists — `repositories-report.html` (→ `repositories.html`) and `contributors-report.html` (→ `contributors-report.html`/`teams-report.html`) — share a search box whose query is split by `;` into terms (`getFilters`); a special term sets a constraint, any other plain term is a name/email filter (plain name terms are a UNION, AND-ed with the constraints):
- `mainLang:<l1>,<l2>` — the **main** language must be one of these (repos: dominant main-aspect extension; contributors: most-active extension). Comma = OR.
- `includesLang:<l1>,<l2>` — contains **any** code in one of these languages even if not the main one. Languages are lowercased file **extensions** (`java`, `cs`, `tf`), the same identifiers `mainLang`/the circle charts use.
  - **Repositories only — scope limiter:** `includesLang:<scope>:<l1>,<l2>` restricts to one scope, where `<scope>` ∈ `main|test|build|generated|other`; unscoped `includesLang:` spans all scopes. An unrecognized scope token is treated as a literal language (so it just matches nothing). Backed by `RepositoryExport.langs` (flat, all scopes) **and** `langsByScope` (per-scope map); both mirrored into the Features-tab rows by `LandscapeDataExport` (`langsOf`/`langsByScopeOf`/`scopeLangs`). Each `includesLang` term is its own AND constraint.
  - **Contributors:** scope does not apply. A contributor's `langs` (on `ContributorReportExport`) is the **30-day commit-based** set — built in `LandscapeReportContributorsTab.buildRecentLangsByContributor()` by inverting the landscape's per-extension `committers30Days` (the **same** data the Overview "Contributors Per File Extension" badges count), so `includesLang:<lang>` on the recent tab matches those badge counts. `mainLang` stays the per-extension helper's biggest extension (`ContributorPerExtensionHelper.getBiggestExtensionLanguage`), independent of that list.
- `team:<text>` — contributors report only; matches the team name.

The **whole query** can be passed in the URL **fragment** (`repositories.html#mainLang:cs,java;customer`, `contributors-report.html?tab=recent#includesLang:go`) and is seeded verbatim into the box by `applyQueryFromHash` (decoded, re-applied on `hashchange`). It lives in the fragment (not a `?query`) so the embedded-data HTML stays cached and, for the contributors report, coexists with the `?tab=` that selects the Recent/All/Bots tab. **Clickable affordances drive these:** in-table language icons call `filterByLang(lang)` (replaces the box with `mainLang:<lang>` and re-renders); the Overview language badges are links — "Lines of Code in **&lt;scope&gt;** Code" → `repositories.html#includesLang:<scope>:<lang>` (scope-matched so the opened list matches the section), "Contributors Per File Extension" → `contributors-report.html?tab=recent#includesLang:<lang>` (`InfoBlocks.addLangInfoBlock`/`addLangInfoBlockExtra` take a `link`; `repositoriesByLangLink`/`contributorsByLangLink` build it). **Info-block links use `display:block; height:100%`** on the anchor so it covers the whole card — an inline `<a>` around the block-level icon/value/label divs collapses to a fragmented click area (the cause of "clicking the icon sometimes does nothing").

**The landscape config's `analysisRoot` must be `"."` in the default layout** (`<root>/_sokrates_landscape/config.json`): `LandscapeAnalyzer.getRepositoryAnalysisFile` resolves a stored root that starts with `.` against the landscape folder's parent, which is right only for `"."` — a relative `"./acme"` (what a CLI gets when a per-organization root is built from the default `-analysisRoot .`) becomes `./acme/./acme` and the landscape silently finds 0 repositories. `LandscapeAnalysisInitiator.analysisRootPath(root, configFile)` therefore stores `"."` whenever the config's grandparent is the root (anything else keeps the given path), and `LandscapeAnalysisUpdater` normalizes an existing non-`"."` value to `"."` in that layout on update (so older broken configs heal on the next run). Discovery (`LandscapeAnalysisInitiator.isSokratesAnalysisFile`) ignores any `data/data.zip` inside a `_sokrates_landscape` folder (`LandscapeAnalysisUtils.isInLandscapeFolder`) — a landscape's own packaged data is not a repository (before this, a re-run registered the landscape itself and skipped it with a warning). Both covered by `LandscapeAnalysisInitiatorTest` and `AnalyzeGitHubOrgCommandTest.relativeAnalysisRootFindsTheRepositories`.

**AI Insights tab (landscape-level aggregation of the sokrates-skills findings).** `reports/landscape/ai/AiInsightsAggregator.aggregate(repositories, landscapeFolder, prefix)` reads, for every repository, `<repo>/reports/ai-insights/<scanner>.json` (resolved lexically from the landscape folder + `repositoryReportsUrlPrefix` + the link's `analysisResultsPath`, so it works before the folder exists; `combined-report.json` and `scanner: "combined"` are skipped; unreadable files logged and skipped) into `AiInsightsLandscapeExport` (`repositories[]`: `AiRepositoryExport` with `insightsUrl`/`reportUrl` relative to the landscape folder, `scannedAt` = latest `analyzed_at`, per-scanner `AiScannerExport`, counts per severity and above-info "attention"; `findings[]`: `AiFindingExport` with severity normalized to critical/high/medium/low/info, description/recommendation/summary shortened to 320/240/400 chars, `url` = the repository explorer's deep link `index.html#<URL-encoded finding id>`). The format is owned by sokrates-skills (scan-core `schema/findings.schema.json`); only `scanner` + `findings[]` are required. `LandscapeReportGenerator.exportAiInsightsData` runs it before the data-only return and writes `data/ai-insights.json` (so it lands in the landscape's `data.zip`); when non-empty, `addTabsLine` adds "AI Insights (N)" after Topology and `addAiInsightsTab` writes `ai-insights.html` from the client-rendered `templates/landscape-ai-insights.html` (`ExplorerTemplate`, compressed `${data}`; Findings view with severity tiles that filter, `;`-term search — `severity:`, `min:`, `confidence:`, `scanner:`, `repo:`, `group:`, `tag:` constraints, plain terms = text union — click-to-sort, show-more paging, query in the URL fragment; Repositories view) and iframes it. Tests: `AiInsightsAggregatorTest` (reports) and the end-to-end `LandscapeAiInsightsTest` (cli: a -postAnalysis hook writes a findings file into the clone, the landscape gets the tab/page/data entry; none without findings).

Two ways to create **sub-landscapes** (shown in the parent's "Sub-landscapes" tab, which reads each child's pre-generated `data/landscapeAnalysisResults.json` + `config.json` and links via `repositoryReportsUrlPrefix + indexFilePath`):
- **Folder-based** — move repository report folders into sub-directories that each have their own `_sokrates_landscape/`. Discovered by scanning for `_sokrates_landscape/index.html` (`LandscapeAnalysisInitiator`, `LandscapeAnalysisUtils.findAllSokratesLandscapeConfigFiles`).
- **Virtual landscapes** — defined by repository-name regex patterns in the parent `config.json` (`virtualLandscapes`: `landscapes[]` with `metadata`/`includeRepoNamePatterns`/`excludeRepoNamePatterns`, plus `remainderLandscapeMetadata`); no folder moves. `VirtualLandscapeBuilder` partitions the parent's already-loaded repositories (multi-membership allowed; the **Remainder** landscape collects unmatched repos) into child `LandscapeAnalysisResults`, and `LandscapeAnalysisCommands.generateVirtualLandscapes` renders a full report per virtual landscape into `_sokrates_landscape/landscapes/<name>/_sokrates_landscape/`, registering each as a **virtual** `SubLandscapeLink` (resolved relative to the landscape folder, no URL prefix). The child's contributor/team topology graphs read pre-computed people-dependency data, so after setting the child config `generateVirtualLandscapes` calls `LandscapeAnalyzer.updatePeopleDependencies(child)` (public static, reused from the analyzer) — otherwise those graphs are empty. The sub-landscape zoomable-circles/sunburst visuals also group repos by virtual landscape (via `buildVirtualLandscapeCircles` in `LandscapeReportGenerator`) instead of by folder path when virtual landscapes are configured. The generated `landscapes/` tree is excluded from folder discovery via `LandscapeAnalysisUtils.isInGeneratedVirtualLandscape` so virtual landscapes aren't picked up twice. A `VirtualLandscapeConfig` may itself carry a nested `virtualLandscapes` (**unlimited depth**): `generateVirtualLandscapes` recurses, partitioning each virtual landscape's own repositories and rendering them under `…/landscapes/<parent>/_sokrates_landscape/landscapes/<child>/_sokrates_landscape/`; `childConfiguration(root, metadata, nested, depth)` climbs `depth * 3` `../` levels (each nesting descends 3 folders) so repo links still resolve to the shared repository folders, and registers the nested links on the child's config so they show in the child's own Sub-landscapes tab. The feature is inert when `virtualLandscapes.landscapes` is empty (backward compatible). Both kinds coexist.

## Two HTML rendering mechanisms

Reports are produced in two distinct ways — know which one you're touching. In both, **repository-controlled strings** (file/folder names, unit names, git author names and emails, meta-derived concern/component names, file extensions) are data, not HTML: server-rendered code passes them through `reports/utils/HtmlEscapeUtils.escape` (element content and single- or double-quoted attribute values) and builds source-viewer links with `HtmlEscapeUtils.viewerFileHref` (percent-encodes the path for the `#aspect=&file=` fragment so `#`, `&`, `%`, `+` and spaces survive `viewer.html`'s `param()`); client templates escape with their local `esc`/`escapeHtml` helper before any `innerHTML`, and d3 code sets names with `.text()` (never `.html()`, which is `innerHTML` on an SVG element and lets an `<img onerror>` escape into HTML); the force-graph templates escape the node id in `nodeLabel`, which the library renders as HTML. `RichTextReport`'s String-taking methods (`addHtmlContent`, `addTableCell`, `addListItem`, `startSubSection`, `addTab`, …) take HTML by contract; **the default path for a repository-controlled string is one of the escaping text primitives** (`addText`, `addParagraphText`, `addListItemText`, `addTableCellText`, `addContentInDivText`, `addTabText` (label only), `startSubSectionText`), which escape and delegate, so passing markup is the thing you write on purpose. The classification is an explicit list in the test, not a name suffix. Tab and section **ids** (`addTab`/`addTabText`/`startTabContentSection`) land in an `id='…'` attribute and an `onclick` JS string, for which `escape` is the wrong encoder; the tripwire checks `addTab`'s arguments like any sink but not the structural `startTabContentSection`/`addTabText` ids, which today carry code or config values (decomposition names). Where text is mixed with hand-built markup (a `<br/>` between two paths, a name inside an `<a>`, SVG `<title>`s, `title='…'` pieces) the explicit `HtmlEscapeUtils.escape` stays; `SimpleOneBarChart` escapes its left text itself (its right text is HTML by contract). `reports`' `RichTextReportSinkEscapingTest` is the tripwire: it scans `reports/src/main` for `<RichTextReport var>.<HTML method>(…)` calls whose arguments carry a repository-controlled getter (`getName`/`getRelativePath`/`getPath`/`getShortName`/`getEmail`/`getUserName`/`getFromComponent`/`getToComponent`) with no known escaper (`HtmlEscapeUtils.escape`/`viewerFileHref`/`encodeFragmentComponent`, `getSafeFileName`, `dependenciesFileNamePrefix`, `getFeatureOfInterestCard`, `getPercentageSvg`) enclosing it, (position-aware: `getPercentageSvg` protects only its left text, `viewerFileHref` only the path; method references like `SourceFile::getName` count as getters), and it fails when a new `RichTextReport` method is not classified as HTML sink, structural (ids/styles/links) or text primitive. It does not follow values through locals, fields, `StringBuilder`s, other helpers, method-returned or lambda-typed receivers, or a statically imported `escape`, so a clean run is not a proof; `cli`'s `ReportHtmlEscapingTest` runs the analyzer over a metacharacter fixture (payload file, folder, depth-2 component and two author identities) and fails if a raw payload reaches a **server-rendered** `.html`; it cannot see the client-rendered pages (explorers, viewer, visuals), whose data is embedded compressed — those rely on the template escapers being attribute-safe (all of them escape `& < > " '`) and on the manual node/browser checks.

1. **Server-rendered (`RichTextReport`)** — most reports. Java code builds the HTML imperatively via the `RichTextReport` builder API (`startTable`/`addTableCell`/`startTabContentSection`/…) in `reports/core/`. Tabs, tables, and inline SVG are all emitted as strings from Java. Shared chrome (CSS, tab JS, the report header `<head>`) lives in `reports/core/ReportConstants.java`.

2. **Client-rendered templates** — static HTML shells with `${...}` placeholders that get the data embedded as JSON and do all rendering in the browser. `common/.../renderingutils/ExplorerTemplate.render(...)` substitutes `${data}` plus any extra placeholders (`${langIcons}`, `${features}`, `${options}`, …). This keeps very large landscapes small and adds client-side **search + click-to-sort + show-more paging** in the browser. **The data is embedded compressed**: `${data}` becomes a `sokratesInflate("<deflate+base64 JSON>")` call and a `${sokrates-inflate-lib}` head block (fflate + the `sokratesInflate` helper, shared with `VisualizationTemplate`) is injected, so the page inflates the inline JSON in-browser. Each report stays self-contained (works from `file://`, no fetch). When validating template JS under node (below), `${data}` is now a function call, not a JSON literal — stub it as `sokratesInflate = () => <fixture>`. Templates live in two folders:
   - `common/src/main/resources/templates/` — the tabular landscape reports: `repositories-report.html` (→ `repositories.html`), `files-explorer.html`, `contributors-report.html` (the searchable Recent/All/Bots list, written to `contributors-report.html`/`teams-report.html` and iframed with `?tab=`; it **replaced** the old server-rendered `contributors.html`/`contributors-recent.html`/`bots.html`/`teams.html` tables, which are no longer written — the `report()` list dropped them and `LandscapeReportContributorsTab.collectLinkedContributors` now computes the linked-contributors set that gates individual-report generation), `contributor-report.html` (the per-person individual report — a shared static page whose data archive is embedded inline, opened as `contributors/<contributor|team>-report.html#<safe-email>` — the person key is in the URL **fragment**, not a `?key=` query param, so the browser caches the one HTML file once and reuses it for every person; a `hashchange` listener re-renders without reloading). It `sokratesUnzip`-extracts the `<key>.json` entry from an archive embedded inline as base64 (`var SOKRATES_ARCHIVE = "<b64-zip>"`, via `${embedded-archive}` + the `${sokrates-unzip-lib}` head block) — no fetch, opens from `file://`. Each per-person entry bundles `{data, options}`; teams are still flagged by `isTeam` in the data. **Language icons are NOT carried per person** — they are large base64 data URIs identical across everyone, so the page injects ONE shared map (`var SOKRATES_LANG_ICONS = {...}`, via the `${lang-icons}` placeholder) covering every language used by anyone in that file, and `langIcon(lang)` looks up that global map. The producer accumulates the union of language keys in a reserved `__langs.json` zip entry (so it survives the cross-call merge) and resolves the icons once via `DataImageUtils.getLangDataImageMapJson`; `__langs.json` is stripped from the page's embedded archive (which holds only person entries). **The people are split across THREE self-contained files so no single file grows huge on big landscapes** (one shared file hit ~60 MB for 5000 developers): **recent** contributors (a commit in the last 30 days — the landscape's `getCommitsCount30Days() > 0` rule) → `contributor-report.html` (small, the common/default case; archive `people.zip`); **everyone** (recent + non-recent contributors + bots) → `contributor-report-all.html` (the big, rarely opened file; archive `people-all.zip`); **teams** → `team-report.html` (archive `teams.zip`). Each file embeds only its own archive inline and still works from `file://`. All three are written from the **same** template resource by `LandscapeIndividualContributorsReports.getIndividualReports(list, isTeam)`: for `isTeam=false` it writes the recent subset to `contributor-report.html` AND the full list to `contributor-report-all.html` (via the `writeReport` helper); for `isTeam=true` it writes `team-report.html`. Called once per group (contributors then bots, both `isTeam=false`; teams `isTeam=true`); the on-disk zip per file is the cross-call merge accumulator (bots accumulate into `people-all.zip` only — they're never recent). Links are routed by `getContributorReportUrl(email)` / `getContributorUrl(email)`, which check two sets seeded eagerly in `LandscapeReportGenerator`'s constructor (each cleared per landscape so virtual/sub-landscapes don't cross-route): `registerTeams(getTeams())` and `registerRecentContributors(getContributors())`. A team email → `team-report.html`; a recent contributor → `contributor-report.html`; everyone else → `contributor-report-all.html`. The page's link key = `SystemUtils.getSafeFileName(email).toLowerCase()`; nothing must touch `data` at script-eval time since it's assigned after the in-page extract. The per-repository report's **Files**, **Units**, and **Commits** tabs also use this mechanism: `files-explorer.html`, `units-explorer.html`, and `commits-explorer.html` are generated by `FilesExplorerGenerators`/`UnitsExplorerGenerators`/`CommitsExplorerGenerators` (`reports/.../generators/explorers/`) into `<reports>/explorers/` from `FileExport`/`UnitExport`/`CommitsExplorerData` DTOs, and embedded as iframes by `ReportFileExporter` (the Commits tab id is `commits-explorer` — plain `commits` is taken by the Activity tab). Selecting commits (click / ⌘-or-ctrl+click / shift+click range / ↑↓ keys / esc) turns their files red — purple for paths that no longer exist (scope `deleted`, sized by a largest-lines-added/deleted proxy), which enter the tree only while a selected commit references them. Selection is keyed by the stable `idx` property resolved via the `commitsByIdx` snapshot — never by position into the in-place-re-sorted `commits` array. No per-commit file list survives analysis, so `CommitsExplorerGenerators` re-reads `git-history.txt` line-by-line via `GitHistoryUtils.parseLine` (NOT `getHistoryFromFile` — JVM-wide static cache) and groups by sha; commits are capped at the newest `MAX_COMMITS` (10,000; page shows “newest N of M”), shas shortened to 10 chars, and commits reference files by index into a shared path list so each path is embedded once.
   - `common/src/main/resources/vis_templates/` — visualisations rendered with third-party JS pinned to a CDN version: `force_2d.html`/`force_3d.html` (force-graph; node list is searchable/toggleable), `bar_chart_races.html` (d3 racing chart), and the d3 pack-layout `zoomable_circles.html`/`zoomable_sunburst.html`. This keeps each file self-contained (works from `file://`, no fetch) while shrinking it (e.g. the all-files circles dropped ~83KB→~12KB). Dropped these files ~1.3MB→~5KB.

   The per-repository **Structure** report (`reports/.../templates/Structure.html`, shown as an iframe on the report home page) is a tab strip of these circle/sunburst visuals. The CLI's `generateVisuals` (`CommandLineInterface`) writes the backing `visuals/zoomable_circles_*.html` files: `zoomable_circles_<scope>.html` per scope (main/test/build/generated/other), the risk-colored `..._<metric>_coloring[_categories].html` for the main scope, and `zoomable_circles_all_files.html` — the default "All Files" tab, which merges every scope's files into one folder-structure tree (`PathStringsToTreeStructure.toVisualizationItems(Map<SourceFile,String>)`) and color-codes each **file leaf** by its scope (folders stay on the depth gradient). The scope-color constants in `CommandLineInterface` (`SCOPE_COLOR_*`) and the legend swatches in `Structure.html` must stay in sync.

   The per-row JSON shapes are DTOs under `reports/.../landscape/data/` (e.g. `RepositoryExport`/`RepositoryReportData`, `ContributorReportExport`, `ContributorIndividualReportExport`). `LandscapeDataExport` and `LandscapeReportContributorsTab`/`LandscapeIndividualContributorsReports` build the data and render the templates. **The template (JS render logic) and its DTO move together** — change both when adding a field. These reports do *not* apply server-side list caps (paging handles scale); don't reintroduce a `getContributorsListLimit`-style truncation. Validate template JS by extracting the `<script>` blocks, stubbing the placeholders, and running `vm.compileFunction` (or a small DOM stub) under node before regenerating a landscape.

## Source-code cache: the `src/` tree (one shared viewer, archive embedded inline)

The per-repository report's `<reports>/src/` folder holds the source code referenced by the reports. To avoid emitting 1000+ tiny files per repo (slow to sync/upload), it is rendered by a **single client-side viewer** rather than one HTML page per snippet, and to let reports open from `file://` (no web server) the viewer's whole data archive is **embedded inline in `src/viewer.html`** rather than fetched. `DataExporter.exportSourceFile()` (`reports/.../dataexporters/DataExporter.java`) collects the data into `viewerArchiveEntries` (a `Map<entryName, content>`) and writes only `src/viewer.html` (last, via `saveViewerFile()`):

- **Source files** — gated by `analysis.saveSourceFiles`, collected per scope (main/test/generated/buildAndDeployment/other) by `collectAspectSourceFiles`, keyed **`<aspect>/<relativePath>`** (the viewer computes this key from `?aspect=&file=`). Only files in `getReferencedFiles()` (the ≤9 top-N lists, capped by `maxTopListSize`) are included. (The aspect's plain file-list JSON is still written to `data/<aspect>FilesPaths.json` — a separate loose `data/` contract.)
- **Fragment bundles** — gated by `analysis.saveCodeFragments`, collected by `collectUnitFragments`/`collectDuplicateFragments` under key **`fragments/<type>.json`**. Unit lists (`longest_unit`, `most_complex_units`) → array of `FragmentExport` (`{name,file,from,to,loc,mccabe,ext,code}`, `reports/.../dataexporters/units/`). Duplicate lists (`longest_duplicates`, `most_frequent_duplicates`, `unit_duplicates`) → array of `DuplicateFragmentExport` (`{ext, blocks:[{file,from,to,code}]}`, `reports/.../dataexporters/duplication/`). Array order matches the source list order; reports link to a 1-based index.
- **`src/viewer.html`** — one shared client-rendered viewer (highlight.js v11 + `highlightjs-line-numbers.js` + fflate, all CDN-pinned). `saveViewerFile()` zips `viewerArchiveEntries` (`ZipUtils.stringEntriesToZipBytes`), base64s the bytes (`VisualizationTemplate.base64`), and substitutes them into `${embedded-archive}` (`var SOKRATES_ARCHIVE = "<b64-zip>"`) + injects `${sokrates-unzip-lib}`. The page `sokratesUnzip`-extracts in-browser: `?aspect=<a>&file=<path>[&from=&to=]` reads entry `<a>/<path>` and highlights it; `?bundle=fragments/<type>.json&i=<1-based>` reads that bundle entry, parses, and renders item i (units via `renderUnit`, duplicates via multi-block `renderDuplicate`). Line numbers start at the fragment's real `from` line. **No `src/*.zip` or `src/fragments/*.json` are written — `src/` holds only `viewer.html`** (report-only and freely restructurable; only `data/*` is an external-tooling contract).

**The viewer's render JS and these DTOs are a contract — the JSON field names (and the archive keys) must match.** When adding a field, change the DTO and `viewer.html` together (mirrors the landscape template/DTO rule above); when changing an archive key, change both the `DataExporter` `put(...)` key and the viewer's key computation. Five report link sites point at the viewer: `UtilsReportUtils` (unit file link + unit fragment link), `FilesReportUtils` (file-table link), `DuplicationReportGenerator` (duplicate "view"), and `FilesExplorerGenerators`/`UnitsExplorerGenerators` (explorer links) — their `?aspect=&file=` / `?bundle=&i=` must resolve to a collected key. A link's index must stay aligned with its bundle's array order; the duplication table caps displayed rows at `MAX_TABLE_ROWS_COUNT` but the bundle holds all (indices within the cap still align). The viewer opens from `file://` (data is inline, no fetch); it still needs CDN access for highlight.js/fflate. Validate `viewer.html` JS the same way as other template JS (extract `<script>`, stub `${embedded-archive}` as `var SOKRATES_ARCHIVE=""` and `${sokrates-unzip-lib}` as empty / a `sokratesUnzip` stub, run under node).

## The `data/` folder is one `data.zip` (read by reports AND landscape)

The per-repository `<reports>/data/` folder (all JSON exports + `data/text/*.txt` + execution
stats + textual summary) is packaged into a single **`data/data.zip`** — the loose files are
removed. `DataExporter.zipDataFolder()` does this; the CLI calls it as the **final** data step
(after `saveExecutionStats`/`saveTextualSummary`, so those are inside the zip too). Entry names
are paths relative to `data/` (e.g. `analysisResults.json`, `text/aspect_main.txt`).

`zipDataFolder()` also writes a sibling **`data/data-preview.html`** (`DataExporter.writeDataPreview`,
shared with the landscape's `zipLandscapeDataFolder`): a client-rendered preview that embeds the
whole archive inline as base64 (`${embedded-archive}` + `${sokrates-unzip-lib}`), reads `?entry=…`,
and shows that one entry (pretty-printed JSON / raw text / "binary — download only") with a
per-entry Download button — all from `file://`, no fetch. `data.zip` itself stays as the
whole-archive raw-data contract.

Two consumers, both updated to read from the zip — **this is a cross-run contract**:
- **HTML reports**: data links call `downloadDataFile('<entry>')` (in
  `ReportConstants.REPORTS_HTML_HEADER`) which now opens `data-preview.html?entry=<entry>` (no fetch;
  it picks `../data/` for per-repo reports in `html/` vs `data/` for landscape reports at the root).
  The preview shows the entry and offers a Download button — so this works from `file://`.
- **Landscape**: `LandscapeAnalyzer` reads `analysisResults.json` + `config.json` +
  `text/aspect_*.txt` + `text/mainFilesWithHistory.txt` from each repo's `data.zip`
  (`readDataEntry` → `readDataZipEntry`, plain `java.util.zip` — codeanalyzer has no `reports`
  dep). **Backward-compatible: zip first, then a loose-file fallback** — `readDataEntry` reads
  `data/<entry>` directly when there's no `data.zip` (older reports), so a landscape can mix
  current (zipped) and older (loose) repositories. Discovery (`LandscapeAnalysisInitiator`)
  likewise finds repos by `data/data.zip` OR a loose `data/analysisResults.json` (the latter only
  when there is no sibling `data.zip`, so a repo is never registered twice); the
  `SokratesRepositoryLink` always records the conceptual `data/analysisResults.json` path (its
  parent folder is where the analyzer reads from). A repo with neither is skipped (logged). The
  landscape's OWN `_sokrates_landscape/data/` is packaged the same way by
  `LandscapeAnalysisCommands.zipLandscapeDataFolder` (its own `data.zip` + `data-preview.html`; it
  deletes any prior preview before merging so the preview is never folded into `data.zip`). When
  changing the data entry names or the landscape read sites, keep producer (`DataExporter`) and
  consumer (`LandscapeAnalyzer` + `LandscapeAnalysisInitiator`) in sync.

## Dependency graphs (Mermaid, client-side — no Graphviz)

Dependency/visualization graphs (component, file-temporal, duplication-between-components, contributor-shared-files, and all landscape graphs) are rendered **client-side with Mermaid.js**, not server-side Graphviz. There is no external `dot` process and no per-graph `.svg`/`.dot.txt` files.

- **Producer**: `GraphvizDependencyRenderer.getMermaidContent(allComponents, deps, groups)` (`reports/.../utils/`) emits a Mermaid `flowchart` (the legacy `getGraphvizContent` DOT producer is unused by reports). Configured by the same setters (`setTypeGraph`/`setTypeDigraph` → undirected `---` vs directed `-->`, `setOrientation` → `flowchart TB/LR/…`, `setArrowColor`/`setCyclicArrowColor`, `setDefaultNodeFillColor`, `setMaxNumberOfDependencies`, `setReverseDirection`). Nodes get **synthetic ids** (`n0`,`n1`,…) with the real name in the `["label"]` (Mermaid ids can't hold arbitrary chars). Labels are repository-controlled (component/folder/file names) and Mermaid renders them as HTML, so `escapeMermaidLabel` writes `& " < >` as Mermaid entity codes (`#amp;` `#quot;` `#lt;` `#gt;`, decoded by mermaid.js) and the definition never carries raw markup; every `mermaid.initialize` site (`REPORTS_HTML_HEADER`, `standaloneMermaidPage`, and the unused `templates/mermaid.html`) runs with **`securityLevel: 'strict'`**, and `ReportRenderer.mermaidBlock`/`standaloneMermaidPage` HTML-escape the `<pre>` text (and the download stash, which `downloadMermaid` decodes via a textarea) as a second layer. Edges are emitted in count-desc order and each gets a `linkStyle <index> stroke:…,stroke-width:…px` line — **`linkStyle` targets edges by definition-order index, so edge ordering is load-bearing** (covered by `GraphvizDependencyRendererMermaidTest`). Graphviz X11 colour names are mapped to CSS via `toCssColor` (e.g. `deepskyblue2`→`#00b2ee`).
- **Embedding**: callers still call `RichTextReport.addGraphvizFigure(id, desc, content)`; the content is now Mermaid. `ReportRenderer.mermaidBlock(id, def)` emits the fragment as `<pre class="mermaid">…</pre>` (HTML-escaped as element text, and **not** through `minimize()`, which would corrupt the layout-sensitive text), preceded by a hidden `<script type="text/plain" id="mermaid-source-<id>">` holding the same definition. **No `.mmd` files are written to disk**: the "download .mmd" link (the `addDownloadLinks` helpers + the `downloadMermaid(id)` JS in `REPORTS_HTML_HEADER`) builds the file in the browser from that embedded source as a `Blob` — mermaid.js overwrites the `<pre>` with SVG on render, so the source must be stashed in the script tag to survive. Mermaid.js is loaded once via `ReportConstants.REPORTS_HTML_HEADER` with **`startOnLoad: false`** — a diagram laid out inside a hidden container (a collapsed `<details>` show-more block or an inactive tab) has zero size and Mermaid 10 throws "Syntax error in text". So rendering is **lazy and visibility-gated**: `renderMermaidIn(container)` runs only the visible, not-yet-processed `pre.mermaid`, called on `DOMContentLoaded`, on each `<details>` `toggle`, and on tab open (`openTab`). When adding a new collapsible container type, make sure its diagrams get a `renderMermaidIn` trigger. Standalone graph pages (previously `.svg`) are written as self-contained Mermaid HTML via `VisualizationTools.standaloneMermaidPage`.
- **Reports must be served over/opened in a browser with CDN access** for mermaid.js (same constraint as the source viewer). Force-graph/d3 visuals are a separate mechanism and were untouched. The Swing/JavaFX explorer's inline graph preview was dropped (it required Graphviz); the explorer shows the dependency text + matrix instead.

## Conventions when modifying analysis behavior

- The regex-driven, heuristic nature of dependency/unit extraction means analyzers are approximate by design — match the existing heuristic style rather than attempting full parsing.
- Adding a new analysis usually means: new `Analyzer` subclass + a results field on `CodeAnalysisResults` + a matching report generator. The three stay in lockstep.
- Defaults (default concerns, default tag rules, default goals/controls) are generated in code in `CodeConfiguration` — extend those methods rather than hardcoding into the JSON template.
- Meta-rule `nameOperations` (`metaConcerns`/`metaComponents`/`metaRules`) run the `sourcecode/operations` string ops (`extract`, `replace`, `remove`, `trim`, `prepend`, …; same ops as `transformContributorEmails`). **`extract` returns capture group 1 when the regex defines one**, otherwise the whole match (`ExtractRegexOperation`). This matters because `MetaRulesProcessor` dedups aspects by the exact produced name: a whole-line match (`.*foo.*`) keeps leading indentation in the name, so one concern splits into one entry per indentation level.

## Per-repository report notes

- **Overview (`index.html`) activity table** (`ContributorsReportUtils.addContributorsPerTimeSlot` with an `ActivitySummary`): only the **30 days** total is a real leading column (`addSummaryCell`, `SUMMARY_WINDOW_DAYS[0]`); the 30 days / 90 days / all time totals all go into each metric icon's hover `title` (`summaryTooltip`), and the icon links to its report (`SUMMARY_METRIC_REPORT`: churn & file updates → `FileChurn.html`, commits → `Commits.html`, contributors → `Contributors.html`). The Overview **Activity** tab (`ReportFileExporter` `commits` section) and the Commits report build the summary for their **Per Year** charts only (month/week/day charts stay plain) with the wider `ACTIVITY_WINDOW_DAYS` (`{30, 90, 180, 365, all}`) and `columns = all`, so there every window is a leading column (`ActivitySummary.days`/`columns`; labels via `windowLabel`); without a summary the icon is plain. An **"AI co-authored commits" row** (`bot` icon, purple bars on the same scale as the commits row so it reads as the AI share; cell title `<slot>: N of M commits (P%)`, summary tooltip `N of M (P%)` per window via `SummaryMetric.AI_COMMITS` → `Commits.html`) is emitted **only when some slot has `aiCoAuthoredCommitsCount > 0`**, so histories without the trailers sidecar render exactly as before.
- **Overview "Features of interest" cards** come from `SummaryUtils.getFeatureOfInterestCard`: fixed `FEATURE_CARD_WIDTH` and a fixed two-line name box (`-webkit-line-clamp: 2` + ellipsis) so every card is the same size; the full name is HTML-escaped and in the `title`.
- **Features of Interest report** (`ConcernsReportGenerator`): each concern links to two exported text files — `text/aspect_<x>_found_text_per_file.txt` (per-file matched lines, from `getFoundFiles()`) and `text/aspect_<x>_found_text.txt` (unique matched texts + counts, from `getFoundTextList()`); `DataExporter.saveFoundTextPerFile`/`saveFoundText` write them.
- **Components report** (`LogicalComponentsReportGenerator`): one tab per logical decomposition; everything inside a tab — including the temporal "dependencies between components in same commits" section — must be built from **that** decomposition only (`addDependenciesSection(key, …)`), never by looping over all decompositions.
