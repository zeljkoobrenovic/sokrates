What an AI coding agent would spend writing the main code again, the way a good team works: small commits with tests, fixes after debugging, refactoring, and redoing the share of the work that the uncertainty says will not deliver.

All amounts are base AI costs: the agent's tokens only, leaving out people's time, discovery, planning, review, integration, infrastructure and every other cost of building software. Use them as a base to see where the levers for using AI effectively are, not as a budget.

How it works

  • In one line: how much an agent would spend writing the main code again, the way a good team works: small, frequent commits, tests with the code, fixes with debugging, and refactoring along the way, redoing what the uncertainty says will not work out.
  • Measured: only the lines of main code (). Everything else is assumed: test code (by default as much as main code), build & other code, and how the work goes.
  • Building: sessions of a commit's size write new code and its tests, reading surrounding code for context.
  • Uncertainty: how sure we are that what gets built delivers the intended value. Low is a migration (the same functionality, in another language); higher levels redo a share of the built work: changed after feedback, thrown away, rebuilt. A share p redone, where a redo can miss again, means building the kept code ÷ (1 − p). The history shows how much it redid in hindsight: lines added ÷ lines today.
  • Fixing: a number of fixes per 1,000 lines built; each is a small change in about 2 files after reading code to find the cause, with its steps multiplied by the debugging factor.
  • Refactoring: a share of the kept code is rewritten in sessions as large as build sessions, reading twice what they change.
  • Every session goes through the same model as the history: steps, context that grows with reads, tool output and output, and cache-priced re-sends.
  • A range, not a measurement: P10–P90 of simulations.
  • In one line: every agent step re-sends the whole context, so a session costs about steps × average context, mostly at cache prices, plus its output.
  • Tasks: commits with the same ticket id (e.g. ABC-123) are one task; otherwise, consecutive commits of one author, at most a day apart, touching overlapping files. Each task is split into sessions of at most 10 files or 400 changed lines.
  • Scopes: main, test, build & deployment and other code count; generated code, unscoped files and unanalyzed extensions do not.
  • Steps: a number per session plus one per touched file. Fix tasks multiply them by the debugging factor: a small fix often follows reproduce, run and inspect loops that git does not show.
  • Context starts at the base context and grows with the reads, the tool output and the output. Reads are the edited files' current total lines (comments and blank lines included, at most 2,000 per file) × tokens per line × read amplification. New files are written, not read; deleted files are free.
  • Output: changed lines × tokens per line × write overhead, plus output per step.
  • Cost: new context at the cache-write price, re-sent context at the cache-read price (cache misses at the input price), output at the output price.
  • Refactoring savings: what files no larger than the max file size would have saved. Every file a session reads counts at most that many lines (a 1,200-line file counts 400, a 330-line file 330; same files, same commits). That saves read tokens, and a carry-over share of the rest of the cost is cut by the same share of reads (fewer steps, less tool output). The cost of the refactoring is not included, and a change that needs several parts of a split file saves less, so the saving is optimistic.
  • Task type groups the results: new code (most lines in new files), refactoring (broad, deletes about as much as it adds), fix (at most 60 lines in at most 3 files) or feature (the rest). Only fix tasks change the model.
  • A range, not a measurement: git cannot see the agent, so steps, tool output, output per step and cache misses are assumptions; the result is P10–P90 of simulations. Steps and cache misses move it most.

  • Smell test: compare the cost per developer-day with the reference (by default about $13, the reported enterprise average for Claude Code). Open-source histories with drive-by contributors land far lower; a large gap for a company team means the assumptions need a look, or that agent-assisted developers do more per day than the history shows.
  • Calibrate with a replay pilot: pick 20–30 tasks of different types and sizes from the CSV, check out each task's parent commit (git checkout <first_sha>^), prompt an agent with the commit message or ticket, record what each session used, compare with the estimate and adjust the assumptions.
  • Token costs only: people's time, discovery, planning, review, integration, infrastructure, licences and operations are not included.
